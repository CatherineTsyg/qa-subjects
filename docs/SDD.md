# Отчёт «на 5»: SDD-версия

Подход: Spec-Driven Development через [GitHub Spec Kit](https://github.com/github/spec-kit) —
конституция → спецификация → уточнение → план → задачи → анализ → реализация.

- Агент: opencode, модель `opencode/deepseek-v4.1-flash-free` (та же, что для `vibe/`)
- Артефакты SDD: `sdd/.specify/` (конституция, шаблоны), `sdd/specs/<фича>/` (spec.md, plan.md, tasks.md и др.)

## Подготовка

```bash
pipx install specify-cli          # specify-cli 1.3.3
cd sdd
specify init --here --force --non-interactive --integration opencode --script sh
```

Init создал `sdd/.specify/` (шаблоны, скрипты, конституция) и `sdd/.opencode/commands/speckit.*.md` (9 команд).
Расширение git не подключалось — ветки под фичи Spec Kit не создаёт.

opencode запускается из папки `sdd/`, чтобы подхватить команды `/speckit.*` из `sdd/.opencode/commands/`.

## Шаги

### 1. `/speckit.constitution`

```
/speckit.constitution Принципы проекта:
- Код живёт только в папке sdd/, папку vibe/ не читать и не использовать.
- Стек: Python 3.12, Django 5.x, PostgreSQL 16, Valkey 8 для кеша, запуск только через docker compose. Веб-порт по умолчанию 8001 (8000 занят другой версией).
- Безопасность: секреты только из переменных окружения, DEBUG по умолчанию False, CSRF на всех POST, права на изменение — только у автора или staff.
- Целостность данных: инварианты (уникальность, допустимые значения) — ограничениями в БД; связанные изменения — в одной транзакции.
- Производительность: без N+1 запросов; часто читаемые и редко меняющиеся данные кешируются в Valkey с явной инвалидацией.
- Тесты обязательны для каждого пользовательского сценария, включая запреты и граничные случаи; тесты кеша проверяют инвалидацию.
- Простота: без лишних абстракций и зависимостей сверх необходимого.
```

Результат: [`sdd/.specify/memory/constitution.md`](../sdd/.specify/memory/constitution.md) v1.0.0 — 7 принципов
(изоляция версий, стек и Docker, безопасность, целостность данных, производительность и кеш, тесты, простота),
ограничения окружения, процесс Spec Kit с quality gates, правила поправок и версионирования.

Ревью конституции:

| # | Что нашёл | Где | Важность | Как исправлено |
|---|-----------|-----|----------|----------------|
| 1 | Разрешена инвалидация кеша внутри транзакции. Если удалить ключ до коммита, параллельный запрос успеет прочитать из БД старые данные и снова положить их в кеш — протухшие данные останутся до следующего изменения. Инвалидировать нужно только после коммита (`transaction.on_commit`) | принцип V | высокая | Инвалидация только через `transaction.on_commit`, внутри транзакции запрещена; добавлено в quality gate 4 и чек-лист ревью |
| 2 | Противоречие: «голосование вместе с пересчётом агрегатов в одной транзакции», хотя по тому же принципу рейтинг не хранится, а считается агрегатом — пересчитывать нечего | принцип IV | низкая | Голос — отдельная транзакция, рейтинг явно «не хранится, вычисляется при чтении» |
| 3 | Требование писать тесты только на `django.test.TestCase` исключает `TransactionTestCase`, без которого не проверить гонки и `on_commit` | принцип VI | низкая | Для гонок и `on_commit` — `TransactionTestCase` или `TestCase.captureOnCommitCallbacks` |

Поправка (промпт 2):

```
/speckit.constitution Поправки к конституции (повысь версию по правилам версионирования):
1. Принцип V: инвалидация кеша выполняется только после успешного коммита — через transaction.on_commit. Инвалидация внутри незакоммиченной транзакции запрещена: параллельный запрос может прочитать старые данные из БД и снова положить их в кеш.
2. Принцип IV: убери «голосование вместе с пересчётом агрегатов» — рейтинг не хранится, а вычисляется агрегатом. В одной транзакции выполняется само изменение голоса.
3. Принцип VI: тесты пишутся на django.test.TestCase; для сценариев с гонками и transaction.on_commit используется TransactionTestCase или TestCase.captureOnCommitCallbacks.
```

Результат: конституция v2.0.0 (MAJOR — по её же правилам ранее разрешённое поведение стало запрещённым), все 3 замечания закрыты.

```
/speckit.plan Django 5.x (приложения accounts и qa), PostgreSQL 16, Valkey 8 как кеш Django

```

Результат: [`plan.md`](../sdd/specs/001-subject-answers/plan.md), `research.md` (12 решений с альтернативами),
`data-model.md`, `contracts/http-endpoints.md` (маршруты, коды ответов, матрица прав, карта инвалидации кеша),

Сильные решения: инвалидация через `on_commit`; кеш хранит словари, а не HTML (не ломает персонализацию);
проверка файлов по сигнатурам без новых зависимостей; `PROTECT` для предмета; выдача файлов через `FileResponse`
(работает при `DEBUG=False`); `gunicorn` + `whitenoise` вместо `runserver`; `assertNumQueries` против N+1.

Ревью плана:

| # | Что нашёл | Где | Важность | Как исправлено |
|---|-----------|-----|----------|----------------|
| 1 | Инвалидация описана только в сервисах и представлениях. Изменения через админку (предметы, правка/удаление ответов staff) и каскады (удаление пользователя удаляет его вопросы, ответы, голоса) кеш не сбросят — протухшие данные, что запрещено принципом V | research R3, plan «Кеш» | высокая | Инвалидация перенесена в сигналы `post_save`/`post_delete` (R3a) с `on_commit`; покрывает админку, management-команды и каскады; тесты на админку и удаление пользователя |
| 2 | Ключи кеша не учитывают пагинацию: `qa:v1:question:{id}:answers` и `qa:v1:subjects:list` — один ключ, хотя списки разбиты на страницы по 20. Непонятно, кешируется весь список (до тысяч ответов в одном значении) или только первая страница | R3, R10 | средняя | Ключи с номером страницы и версией (`…:v{version}:page:{n}`); инвалидация — атомарный `incr` версии, без `delete_pattern` и новых зависимостей |
| 3 | Повтор голосования после `IntegrityError` внутри `transaction.atomic`: в PostgreSQL ошибка прерывает всю транзакцию, повтор без точки сохранения (вложенный `atomic`) упадёт с `TransactionManagementError` | R4 | средняя | Вставка голоса во вложенном `atomic` (точка сохранения) |
| 4 | Скачивание через `FileResponse` без уточнения заголовков: тип содержимого нужно брать из проверенного `content_type`, документы отдавать как `attachment` | R6 | низкая | `Content-Type` из проверенного типа; документы — `attachment`, изображения — `inline` |

| 6 | Кешируемая страница вопроса не описывает персональные данные: как подсветить голос текущего пользователя и скрыть кнопки у его ответов | R3 | низкая | Голоса пользователя — отдельный запрос после чтения кеша, в кеш не попадают |

Исправления плана (промпт):

```
Исправь план (plan.md, research.md, data-model.md, contracts/) по ревью:
1. Инвалидация кеша должна срабатывать при любом изменении данных, включая админку и каскадные удаления (например, удаление пользователя). Регистрируй инвалидацию в сигналах моделей post_save/post_delete через transaction.on_commit, а не только в сервисах; добавь тест на изменение через админку.
2. Учти пагинацию в ключах кеша: ключ включает номер страницы (например, qa:v1:question:{id}:answers:page:{n}); при инвалидации удаляются все страницы — опиши как (версия ключа вопроса или delete_pattern).
3. Повтор голосования после IntegrityError выполняй во вложенном transaction.atomic (точка сохранения), иначе PostgreSQL прервёт всю транзакцию.
4. Скачивание: Content-Type берётся из проверенного content_type, документы отдаются с Content-Disposition: attachment, изображения — inline.
5. Healthcheck web — через python (urllib), а не curl; localhost должен входить в ALLOWED_HOSTS.
6. Опиши, как на кешируемой странице вопроса показываются персональные данные: голоса текущего пользователя запрашиваются отдельным запросом и не кешируются.

```

Результат: все 6 пунктов отражены согласованно во всех артефактах. Агент сам выбрал версию ключа вместо
`delete_pattern` (встроенный `RedisCache` его не поддерживает) и учёл, что `post_delete`-приёмники отключают
fast-delete, поэтому каскады не теряют сигналы.

Замечания на реализацию (не блокируют): в приёмнике сигнала `Vote` вычислять `question_id` сразу, а не внутри
`on_commit`-лямбды (при каскаде ответ к тому моменту уже удалён); `QuerySet.update()` сигналы не отправляет —
не использовать его для изменяемых моделей.
