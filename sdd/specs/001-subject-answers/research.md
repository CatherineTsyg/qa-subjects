# Research: База ответов по предметам

**Feature**: `001-subject-answers` | **Date**: 2026-11-10 | **Plan**: [plan.md](./plan.md)

Все неизвестные Technical Context закрыты: выбор технологий задан пользователем и конституцией,
остальные решения фиксируют способ реализации требований спецификации.

## R1. Аутентификация и регистрация

**Decision**: использовать встроенную модель `django.contrib.auth.models.User` и штатные
механизмы сессий, форм и представлений Django. Приложение `accounts` содержит формы регистрации и
входа, представления и URL; выход — POST-запрос.

**Rationale**: спецификация требует только имя пользователя и пароль; встроенная модель уже даёт
уникальность имени, хеширование пароля, сессии, админку и флаги staff. Это минимальный объём кода
и соответствует принципу простоты.

**Alternatives considered**:
- Собственная модель пользователя с email вместо username — избыточно, усложняет старт проекта и
  миграции, не требуется спецификацией.
- Внешний провайдер входа (OAuth) — не требуется и добавляет зависимости.

## R2. Рейтинг ответа как агрегат

**Decision**: рейтинг вычисляется запросом
`annotate(rating=Coalesce(Sum("votes__value"), 0))`; сортировка —
`order_by("-rating", "-created_at")`. Поле рейтинга в модели не хранится.

**Rationale**: исключает рассинхронизацию между голосами и рейтингом, соответствует принципу IV
конституции. `Coalesce` нужен, чтобы ответ без голосов имел рейтинг `0`, а не `NULL`.

**Alternatives considered**:
- Денормализованное поле `rating` с пересчётом при каждом голосе — быстрее на чтении, но требует
  транзакционной синхронизации и противоречит конституции без явного обоснования.
- Рейтинг в отдельной таблице-агрегате — лишняя сущность и риск рассинхронизации.

## R3. Кеширование, пагинация и версии ключей

**Decision**: использовать `django.core.cache.backends.redis.RedisCache` (Valkey 8). Кешировать:
- страницу списка предметов с числом вопросов —
  `qa:v1:subjects:list:v{version}:page:{n}`;
- страницу отсортированных ответов вопроса с рейтингом и вложениями —
  `qa:v1:question:{id}:answers:v{version}:page:{n}`.

Для каждого набора хранится ключ версии без TTL: `qa:v1:subjects:list:version` и
`qa:v1:question:{id}:answers:version`. Функция `get_version(key)` возвращает
`cache.get(key) or 1`, поэтому первый запрос без ключа версии использует версию `1` и не создаёт
ключ `vNone`. Инвалидация выполняет `cache.add(version_key, 1)` и `cache.incr(version_key)` — обе
операции атомарны. Версия создаётся при первом изменении и увеличивается на каждом следующем,
поэтому все страницы сразу становятся недостижимы; старые записи удаляются по TTL. TTL страниц —
300 секунд. Значения — списки простых словарей (id, текст, автор, дата, рейтинг, метаданные
вложений), без персонального голоса текущего пользователя.

**Rationale**: номер страницы в ключе не даёт разным страницам перезаписывать друг друга;
версия — атомарный способ инвалидировать все страницы без перебора ключей. Встроенный
`RedisCache` не предоставляет `delete_pattern`, а `KEYS`/`SCAN` на каждом изменении вредны для
производительности.

**Alternatives considered**:
- `delete_pattern` — доступен только в `django-redis`, добавляет зависимость и не входит в
  стандартный backend.
- Удалять известные ключи страниц по одной — число страниц заранее неизвестно, возможны пропуски.
- Кешировать весь список без пагинации — противоречит FR-020 и растёт с объёмом данных.

## R3a. Инвалидация через сигналы моделей

**Decision**: инвалидация регистрируется в `qa/signals.py` для `post_save`/`post_delete` моделей
`Subject`, `Question`, `Answer`, `Vote` и `Attachment`. Приёмник не удаляет ключи сразу, а
планирует `transaction.on_commit(lambda: bump_versions(...))`. Нормативное соответствие событий и
инвалидируемых версий задано в
[контрактах](./contracts/http-endpoints.md#кеш-и-побочные-эффекты-нормативная-таблица-инвалидации);
здесь и в других артефактах таблица не дублируется.

В обработчике `Vote` идентификатор вопроса вычисляется в момент сигнала
(`question_id = instance.answer.question_id`) и передаётся в лямбду. Внутри `on_commit` к
`instance.answer` обращаться нельзя: при каскадном удалении ответа связь к моменту коммита уже
удалена.

Сервисы и представления не выполняют инвалидацию сами — сигналы покрывают и админку, и
management-команды, и каскадные удаления, включая удаление пользователя. Подключение
`post_delete`-приёмников отключает fast-delete Django, поэтому каскадные удаления не пропускают
сигналы. При `raw=True` (фикстуры) приёмник сразу выходит.

**Rationale**: единственная точка инвалидации исключает пропуски при изменениях в обход
представлений; `on_commit` сохраняет запрет инвалидации внутри незакоммиченной транзакции
(принцип V). Каскадные `post_delete` срабатывают для каждого удалённого объекта, поэтому удаление
пользователя очищает кеш его вопросов, ответов, голосов и вложений.

**Alternatives considered**:
- Инвалидация только в сервисах/представлениях — пропускает админку, скрипты и каскады.
- Переопределение `save()`/`delete()` моделей — не покрывает `QuerySet.delete()` и каскады.
- Триггеры БД — усложняют миграции и дублируют логику Django.

## R3b. Персональные голоса на кешируемой странице

**Decision**: кеш страницы вопроса содержит только общие данные (текст, автор, дата, рейтинг,
вложения). После чтения кеша отдельным запросом выбираются голоса текущего пользователя для
ответов этой страницы:
`Vote.objects.filter(user=request.user, answer_id__in=[...]).values_list("answer_id", "value")`.
Результат передаётся в шаблон для подсветки кнопок и не кешируется. Для анонима запрос не
выполняется.

**Rationale**: страница остаётся общей для всех пользователей (высокий hit rate), а персональное
состояние всегда актуально и не утекает между пользователями. Это соответствует принципу III
(персональные данные не кешируются) и не создаёт N+1 — один запрос на страницу.

**Alternatives considered**:
- Кешировать `user_vote` в общем значении — покажет чужой голос.
- Отдельный кеш на пользователя — фрагментация и риск утечки персональных данных.
- Не показывать текущий голос — ухудшает UX и противоречит сценарию голосования.

## R4. Конкурентное голосование

**Decision**: операция изменения голоса выполняется во внешнем `transaction.atomic`; при
отсутствии голоса создаётся запись, при наличии — обновляется или удаляется. Вставка выполняется
во вложенном `transaction.atomic` (точка сохранения), поэтому `IntegrityError` от
`UniqueConstraint(user, answer)` откатывает только попытку вставки, а не всю транзакцию
PostgreSQL. После конфликта голос обновляется повторно. В итоге для пары остаётся не более одного
голоса, ошибка пользователю не показывается.

**Rationale**: ограничение БД — гарантия инварианта; повтор после конфликта делает поведение
идемпотентным и соответствует решению из Clarifications.

**Alternatives considered**:
- `get_or_create` без обработки `IntegrityError` — падает при гонке.
- Повтор без вложенного `atomic` — после ошибки PostgreSQL транзакция уже прервана, повтор
  невозможен.
- Блокировка строки ответа (`select_for_update`) — сериализует всех голосующих за ответ и снижает
  пропускную способность; допустимо, но избыточно при наличии уникального ограничения.
- Хранить голоса в кеше — теряет данные при перезапуске и нарушает целостность.

## R5. Проверка загружаемых файлов

**Decision**: валидатор проверяет:
1. расширение из белого списка (jpg, jpeg, png, webp, pdf, txt, doc, docx);
2. содержимое по сигнатуре: JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, WebP `RIFF....WEBP`,
   PDF `%PDF-`, DOC `D0 CF 11 E0 A1 B1 1A E1`, DOCX — ZIP с `[Content_Types].xml`, TXT — без
   нулевых байтов и корректно декодируется как UTF-8;
3. размер: изображения ≤ 5 МБ, документы ≤ 10 МБ;
4. пустой файл отклоняется;
5. количество: не более 5 вложений на ответ (проверка под `select_for_update` ответа).

Имя файла очищается (`os.path.basename`), путь формируется через `upload_to` с датой и случайным
именем. Библиотека `python-magic` не добавляется.

**Rationale**: закрывает требование «проверять не только расширение, но и содержимое» без новых
зависимостей. Подмена расширения ловится сигнатурой; пустой файл — размером 0.

**Alternatives considered**:
- `python-magic`/libmagic — системная зависимость и усложнение Docker-образа.
- `Pillow` для изображений — полезно, но не покрывает документы; для учебного проекта достаточно
  сигнатур, а лишняя зависимость нарушает принцип простоты.

## R6. Хранение, выдача и удаление вложений

**Decision**: `FileField(upload_to="attachments/%Y/%m/%d/")`, файлы — в docker volume `media_data`
(`MEDIA_ROOT=/app/media`). Скачивание — отдельное представление с `FileResponse`, доступное
посетителям; путь на диске не раскрывается. `Content-Type` берётся только из проверенного и
сохранённого `content_type` (не из запроса клиента). Для документов (pdf, txt, doc, docx)
ответ содержит `Content-Disposition: attachment`, для изображений — `inline`. При удалении
вложения файл удаляется через `post_delete`-сигнал; при удалении ответа или вопроса каскад
удаляет вложения и их файлы.

**Rationale**: docker volume переживает перезапуск контейнера; `FileResponse` работает при
`DEBUG=False` и не требует отдачи `MEDIA_ROOT` веб-сервером.

**Alternatives considered**:
- Раздача через `MEDIA_URL` — не работает без DEBUG или отдельного веб-сервера.
- Хранение файлов в БД — противоречит требованию docker volume и ухудшает производительность.

## R7. Удаление предмета

**Decision**: `Question.subject` использует `on_delete=PROTECT`. Удаление непустого предмета
перехватывается в админке и в сервисе: staff видит понятное сообщение, запись не удаляется.
Пустой предмет удаляется штатно. Проверка дополнительно повторяется перед удалением.

**Rationale**: инвариант «непустой предмет удалить нельзя» обеспечивается БД (`PROTECT`), а не
только интерфейсом — принцип IV. `PROTECT` исключает случайное каскадное уничтожение базы знаний.

**Alternatives considered**:
- `CASCADE` — противоречит решению Clarifications.
- Проверка только в админке — обходится через ORM/скрипты.

## R8. Стратегия тестирования

**Decision**: основа — `django.test.TestCase`; общая инфраструктура — `sdd/config/test_utils.py`,
где `LOCMEM_CACHES` переключает кеш на `LocMemCache`, а `TempMediaMixin` подменяет `MEDIA_ROOT`
временным каталогом (`tempfile.mkdtemp()`), очищая его через `shutil.rmtree` после тестов. Эти
утилиты используют все тестовые классы, включая `TransactionTestCase`. Для проверки инвалидации
после коммита — `self.captureOnCommitCallbacks(execute=True)`; отдельно проверяется, что до
выполнения callback ключ ещё существует. Для гонок голосования и сценариев с реальным коммитом —
`TransactionTestCase`. Отдельные тесты: `get_version()` возвращает `1` при отсутствии ключа;
изменение объекта через админку инвалидирует кеш; удаление непустого предмета в админке
отклоняется с сообщением, пустой предмет удаляется; каскадное удаление пользователя очищает кеш
его вопросов, ответов, голосов и вложений; страницы `1..N` кешируются раздельно, а изменение
данных делает все страницы недостижимыми; голос текущего пользователя отображается при общем кеше
страницы; `Client(enforce_csrf_checks=True)` отклоняет POST без CSRF-токена (`403`) для всех
изменяющих действий; голос за удалённый ответ даёт `404`, недопустимый `value` — `400`. Для каждой
страницы — тесты `assertNumQueries`, чтобы исключить N+1.

**Rationale**: `TestCase` быстрый и изолированный; `captureOnCommitCallbacks` позволяет точно
проверить семантику `on_commit` без изменения продакшен-кода; `TransactionTestCase` нужен там, где
важны реальные коммиты и параллельные соединения. Соответствует принципу VI и уточнению v2.0.0.

**Alternatives considered**:
- Только `TestCase` — не проверяет отложенные callback-и и гонки.
- Только `TransactionTestCase` — медленно на всём наборе тестов.

## R9. Развёртывание и healthcheck

**Decision**: Docker Compose с сервисами:
- `db` — PostgreSQL 16, healthcheck `pg_isready`;
- `valkey` — Valkey 8, healthcheck `valkey-cli ping`;
- `web` — сборка из `Dockerfile`, `depends_on` с `condition: service_healthy`, запуск
  `gunicorn config.wsgi:application --bind 0.0.0.0:8001 --workers 4 --threads 4 --timeout 60`;
  healthcheck — Python-скрипт без `curl`:
  `python -c "import urllib.request; urllib.request.urlopen('http://localhost:8001/healthz/', timeout=3)"`.

`web` публикуется на `${WEB_PORT:-8001}:8001`. `localhost` и `127.0.0.1` входят в
`ALLOWED_HOSTS`, чтобы healthcheck проходил при `DEBUG=False`. Статика админки — через
`whitenoise` после `collectstatic`; вложения — через `FileResponse`. `DEBUG=False` по умолчанию.

`collectstatic` выполняется на этапе сборки образа, когда переменные окружения ещё не заданы,
поэтому `Dockerfile` передаёт фиктивный ключ только в этот `RUN`:
`RUN SECRET_KEY=build-only python manage.py collectstatic --noinput`. Ключ не попадает в слои
образа и не используется при запуске; рабочее значение приходит из env контейнера.

**Rationale**: healthcheck не пускает приложение к БД и кешу до готовности зависимостей; `gunicorn`
работает при выключенном DEBUG; `whitenoise` избавляет от отдельного сервиса статики (в схеме
только `web`, `db`, `valkey`).

**Alternatives considered**:
- `runserver --insecure` — dev-сервер в контейнере, нежелателен при `DEBUG=False`.
- Отдельный nginx — четвёртый сервис, избыточно для учебного проекта.
- `collectstatic` без `whitenoise` — админка без стилей.

## R10. Запросы, пагинация и сортировка

**Decision**: список предметов — `annotate(question_count=Count("questions"))`; страница
предмета — `select_related("author")`, пагинация 20, `order_by("-created_at")`; страница
вопроса — ответы с `annotate(rating=...)`, `select_related("author")` и
`prefetch_related("attachments")`, пагинация 20, `order_by("-rating", "-created_at")`.

**Rationale**: `Count` и `Sum` считаются в БД, `select_related`/`prefetch_related` убирают N+1,
порядок соответствует FR-008 и FR-023. Индексы: `Question(subject, -created_at)`,
`Answer(question)`, `Vote(answer)`, `Attachment(answer)`.

**Alternatives considered**:
- Сортировка в Python — загружает все строки и не масштабируется.
- Счётчики в отдельных полях — денормализация и риск рассинхронизации.

## R11. Конфигурация и секреты

**Decision**: настройки читаются из переменных окружения: `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`,
`CSRF_TRUSTED_ORIGINS`, `POSTGRES_*`, `VALKEY_URL`, `WEB_PORT`. Значения по умолчанию безопасны:
`DEBUG=False`, `ALLOWED_HOSTS` по умолчанию включает `localhost`, `127.0.0.1` и `web` (для
healthcheck и обращений из compose), пароли не задаются в коде. `.env.example` содержит все
переменные с локальными значениями.

**Rationale**: принцип III конституции; конфигурация не попадает в образ и репозиторий.

**Alternatives considered**:
- `DATABASE_URL`-парсинг — дополнительная зависимость (`dj-database-url`) без необходимости.
- Хранение `.env` в репозитории — запрещено.

## R12. Интерфейс

**Decision**: серверные шаблоны Django, один базовый шаблон, минимум inline-CSS без внешних
библиотек. Формы — Django Forms с русскими сообщениями об ошибках; пустые состояния и сообщения
об ошибках выводятся в шаблонах. Никакого SPA и API не требуется.

**Rationale**: спецификация описывает пользовательские сценарии, а не программный интерфейс;
шаблоны Django — минимальный путь. Это также упрощает CSRF-защиту и тестирование через `Client`.

**Alternatives considered**:
- REST API + SPA — лишние зависимости, слой и сложность.
- HTMX — не требуется для заявленных сценариев.
