# Сравнение: вайб-кодинг vs SDD

Одно и то же приложение — «база ответов по предметам» — сделано дважды одним агентом (opencode) на одной модели
(`opencode/deepseek-v4.1-flash-free`). Подробности — в [VIBE.md](VIBE.md) и [SDD.md](SDD.md).

## Метрики

| Критерий | vibe | sdd |
|----------|------|-----|
| Время до рабочей версии | _указать_ | _указать_ |
| Промптов к агенту | 2 | 12 |
| Ручных правок кода | 0 | 0 |
| Промежуточные артефакты | — | конституция, спека, план, research, модель данных, контракты, задачи (~2 000 строк) |
| Код приложения (Python, без тестов и миграций) | 978 строк | 1 488 строк |
| Тесты | 40 (687 строк) | 93 (1 572 строки) |
| Шаблоны | 428 строк | 274 строки |
| Кеширование | нет | Valkey: версионные ключи, инвалидация через сигналы и `on_commit` |
| Запуск | `runserver`, `DEBUG=True` в `.env` | `gunicorn` + `whitenoise`, `DEBUG=False`, healthcheck всех сервисов |
| Выдача вложений | только при `DEBUG=True` (`static()`) | `FileResponse` с проверенным `Content-Type`, работает в любом режиме |
| Проверка файлов | расширение и размер | расширение, сигнатура содержимого, пустой файл, размер, количество |
| Проверка производительности | `N+1` нет (проверено вручную) | `assertNumQueries` в тестах + замер p95: 184–465 мс на 10 000 вопросов / 100 000 ответов |

## Где находились дефекты

| Этап | vibe | sdd |
|------|------|-----|
| До написания кода | — | конституция: 3; спека: 6; план: 6; задачи: 7 (ревью) + 14 (`analyze`) |
| В готовом коде | 6 (2 средних по безопасности/надёжности: самоголосование, гонка голосования → 500; ещё лимит файлов, транзакции, `DEBUG`) | 3 низких (кеш на нестандартных `?page=`, удаление файла до коммита, замер без голосов) |

Главное различие — **когда** ловятся ошибки. В вайб-версии дефекты нашлись в уже написанном коде и исправлялись
вторым промптом. В SDD большая часть проблем (инвалидация кеша до коммита, пропуск админки и каскадов,
пагинация в ключах кеша, savepoint при гонке, `collectstatic` без `SECRET_KEY`) была найдена в документах — до
того, как появилась хоть одна строка кода, — и исправление стоило правки абзаца, а не кода и тестов.

## Наблюдения

**Вайб-кодинг**

- Очень быстрый старт: рабочее приложение с тестами — за один промпт.
- Агент сам принимает решения, которых никто не просил и не проверял (например, лимиты, формат ключей, порядок
  сортировки при равенстве); их видно только при чтении кода.
- Нефункциональные требования (кеш, режим `DEBUG=False`, производительность) без явного запроса не появляются.
- Качество результата целиком зависит от ревью: найденные дефекты были реальными (500 при двойном клике,
  накрутка рейтинга).

**SDD (Spec Kit)**

- Каждое решение записано и обосновано (`research.md` — 12 решений с альтернативами); есть трассировка
  требование → задача → тест.
- Конституция работает как постоянный контекст: принципы (инвалидация после коммита, `DEBUG=False`, тесты на
  запреты) соблюдались на всех следующих шагах без повторных напоминаний.
- `/speckit.analyze` хорошо находит пробелы покрытия и рассогласования между документами (нашёл 8 проблем,
  пропущенных ручным ревью, включая реальную ошибку с версией кеша по умолчанию), но не видит проблем среды
  выполнения (сборка Docker) и тонкостей ORM.
- `/speckit.clarify` на этой модели **не нашёл пробелов сам** — дважды ответил «неоднозначностей нет»; решения по
  6 граничным случаям пришлось дать человеку.
- Цена: в 6 раз больше промптов и ~2 000 строк документов, которые нужно прочитать и проверить.

## Оговорки о честности сравнения

- **Утечка опыта из вайб-версии.** На шаге `specify` агент прочитал историю git и отчёт `docs/VIBE.md` и взял
  оттуда запрет самоголосования. Код `vibe/` он не открывал, ссылку на «предыдущую версию» потом убрали, но
  требование FR-011 SDD нашёл не сам.
- **Опыт человека.** Конституция SDD-версии писалась после ревью вайб-версии и уже содержала уроки из неё
  (транзакции, `DEBUG=False` по умолчанию, лимит файлов). Честнее было бы делать SDD первым или поручить версии
  разным людям.
- Одна модель, одна предметная область, один прогон — выводы качественные, а не статистические.

## Выводы

- **Вайб-кодинг** оправдан для прототипов, небольших и хорошо понятных задач, когда важна скорость, а ошибки
  дёшево исправлять: результат достигается за минуты, но корректность обеспечивает только ревью.
- **SDD** оправдан, когда есть нефункциональные требования (кеш, конкурентность, безопасность), несколько
  исполнителей или нужна прослеживаемость решений: дороже по времени и вниманию на старте, зато ошибки
  проектирования находятся в документах, а итоговый код ближе к требованиям и лучше покрыт тестами.
- В обоих подходах качество определяет человек: в вайб-кодинге — ревью кода, в SDD — ревью спецификации и
  ответы на вопросы, которые агент сам не задал.
