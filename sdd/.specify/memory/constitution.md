# Constitution of QA Subjects (SDD)

## Core Principles

### I. Изоляция версий проекта

Рабочая область SDD-версии — только каталог `sdd/`.

- Весь код, конфигурация, миграции, тесты и артефакты Spec Kit создаются и изменяются только внутри `sdd/`.
- Каталог `vibe/` не читается, не анализируется и не используется как источник кода, идей или
  конфигурации.
- Запрещено импортировать, копировать или переносить код между `vibe/` и `sdd/`; две версии
  развиваются независимо.
- Команды запускаются из `sdd/`, пути в документации и скриптах указываются относительно него.

**Обоснование**: независимость версий — условие корректного сравнения подходов; случайное
заимствование кода искажает результат и нарушает границы задачи.

### II. Фиксированный стек и запуск через Docker Compose

Стек зафиксирован и не расширяется без явного согласования.

- Python 3.12, Django 5.x, PostgreSQL 16, Valkey 8 (кеш Django через
  `django.core.cache.backends.redis.RedisCache`).
- Единственный поддерживаемый способ запуска — `docker compose` (сервисы приложения, БД и
  Valkey, healthcheck для зависимых сервисов).
- Веб-порт по умолчанию — `8001`; порт задаётся переменной окружения. Порт `8000` не
  используется: он занят версией `vibe/`.
- Зависимости перечислены в `requirements.txt` с закреплёнными версиями. Мажорные версии
  зависимостей не меняются без согласования.
- Все обязательные переменные окружения описаны в `.env.example` с безопасными значениями по
  умолчанию.

**Обоснование**: воспроизводимость окружения и отсутствие конфликтов с параллельной версией
приложения.

### III. Безопасность и контроль доступа

Безопасность обеспечивается настройками и проверками по умолчанию, а не дисциплиной
разработчика.

- Секреты (`SECRET_KEY`, пароли БД и т. п.) читаются только из переменных окружения. Пароли и
  ключи в коде, репозитории и логах запрещены.
- `DEBUG` по умолчанию — `False`; включение допускается только локально через переменную
  окружения.
- `ALLOWED_HOSTS`, CSRF-защита и cookie-флаги настраиваются из окружения; все POST-запросы
  защищены CSRF-токеном.
- Изменять и удалять вопрос, ответ или вложение может только автор объекта или staff. Для
  остальных пользователей операция завершается отказом `403`; UI не является средством защиты.
- Загрузки проверяются по расширению, размеру и количеству, хранятся в `MEDIA_ROOT` (docker
  volume); путь на диске пользователю не раскрывается.
- Ответы с ошибками не раскрывают внутренние детали (стектрейсы, SQL, пути).

**Обоснование**: приложение публичное и многопользовательское; ошибка в правах или утечка
секрета необратима для данных пользователей.

### IV. Целостность данных и транзакционность

Инварианты данных обеспечиваются схемой БД, а не только кодом приложения.

- Уникальность и допустимые значения выражаются ограничениями БД: `UniqueConstraint`,
  `CheckConstraint`, внешние ключи, `NOT NULL`.
- Голос уникален для пары (пользователь, ответ) на уровне БД; повторный голос обновляет
  существующий, снятие голоса удаляет его.
- Связанные изменения, которые должны быть согласованы (создание/удаление объекта вместе с
  вложениями), выполняются в одной транзакции (`transaction.atomic`). Изменение голоса —
  самостоятельная операция: в одной транзакции выполняется само изменение голоса, пересчёт
  агрегатов в неё не входит.
- Рейтинг ответа не хранится: он вычисляется агрегатом по голосам (`Sum`/`Count`) при чтении.
- Каждое изменение моделей сопровождается миграцией; миграции коммитятся вместе с изменением.

**Обоснование**: гонки и обходные пути через API/админку не должны приводить к рассогласованным
данным; ограничения БД — последний рубеж защиты.

### V. Производительность и кеширование

Списки и страницы не деградируют при росте числа пользователей и данных.

- N+1 запросов быть не должно: связи загружаются через `select_related`, `prefetch_related` и
  `annotate`; число запросов на страницу проверяется в тестах при необходимости.
- Часто читаемые и редко меняющиеся данные (списки предметов и ответов, счётчики, рейтинги)
  кешируются в Valkey.
- У каждого кешируемого набора есть ключ с пространством имён и явная инвалидация при любом
  изменении влияющих данных: создание, изменение, удаление вопроса, ответа, вложения или голоса.
- Кеш не является источником истины: при промахе данные читаются из БД и кешируются заново.
- Инвалидация кеша выполняется только после успешного коммита транзакции — через
  `transaction.on_commit`. Инвалидация внутри незакоммиченной транзакции запрещена:
  параллельный запрос может прочитать старые данные из БД и снова положить их в кеш.
- «Протухшие» данные в выдаче недопустимы.

**Обоснование**: кеш без инвалидации превращается в источник неверных ответов, а N+1 скрывает
реальную стоимость страницы. Инвалидация до коммита оставляет окно гонки, в котором кеш
заполняется устаревшими данными.

### VI. Обязательное тестирование

Тесты обязательны для каждого пользовательского сценария.

- Каждая новая возможность сопровождается тестами на `django.test.TestCase`, которые
  запускаются командой `docker compose exec web python manage.py test`.
- Покрываются успешные сценарии, запреты и граничные случаи: неавторизованный доступ, чужие
  объекты (`403`), отсутствующие объекты (`404`), недопустимые значения, лимиты размера и
  количества файлов, пустые и максимальные значения.
- Тесты кеша проверяют не только попадание в кеш, но и инвалидацию после каждого изменяющего
  действия; в тестах используется `LocMemCache`.
- Сценарии с гонками и проверкой `transaction.on_commit` тестируются через
  `TransactionTestCase` или `TestCase.captureOnCommitCallbacks`; обычный `TestCase` для них не
  используется, так как не выполняет отложенные до коммита callback-и.
- Тест, падающий или нестабильный, блокирует завершение задачи; отключение тестов без
  обоснования запрещено.

**Обоснование**: именно негативные и граничные сценарии содержат большинство дефектов; без
проверки инвалидации кеш ломается незаметно.

### VII. Простота

Решение остаётся минимально достаточным.

- Используются штатные средства Django: ORM, формы, шаблоны, админка, встроенная аутентификация.
- Новые абстракции, слои, сервисы и зависимости добавляются только при доказанной
  необходимости; YAGNI применяется по умолчанию.
- Дублирование устраняется по факту, а не «на будущее»; преждевременная универсализация
  запрещена.
- Любое усложнение (дополнительный сервис, слой, зависимость) обосновывается в плане.

**Обоснование**: простое решение легче проверять, тестировать и сопровождать; сложность —
основной источник ошибок в учебном проекте.

## Additional Constraints

### Ограничения стека и окружения

- Репозиторий не содержит `.env`, `media/`, `__pycache__`, виртуальных окружений и других
  локальных артефактов; они перечислены в `.gitignore`.
- Структура `sdd/`: `docker-compose.yml`, `Dockerfile`, `.env.example`, `requirements.txt`,
  `manage.py`, `config/` (settings, urls, wsgi), Django-приложения.
- Настройки читаются из переменных окружения; значения по умолчанию безопасны для запуска в
  контейнере и не содержат production-секретов.
- Данные PostgreSQL и файлы `media/` сохраняются в docker volumes.
- Мажорные обновления Python, Django, PostgreSQL и Valkey выполняются только по согласованию.

### Границы изменений

- Конституция, шаблоны Spec Kit и служебные файлы `.specify/` не переписываются в ходе
  реализации фич; изменения конституции выполняются отдельной процедурой (см. Governance).
- Файлы `docs/`, `AGENTS.md` и `opencode.json` не удаляются и не переписываются без явной
  просьбы.

## Development Workflow

### Процесс Spec Kit

Разработка идёт по цепочке артефактов: конституция → `spec.md` → уточнения → `plan.md` →
`tasks.md` → анализ → реализация.

- Спецификация фиксирует пользовательские сценарии и критерии приёмки без деталей реализации.
- План проверяет соответствие принципам этой конституции; отклонения обосновываются явно.
- Задачи декомпозируют план до проверяемых шагов и включают тесты.
- Анализ перед реализацией выявляет расхождения между спецификацией, планом и задачами.
- Реализация не начинается, пока спецификация и план не согласованы.

### Quality gates

Изменение считается завершённым, когда одновременно выполнено:

1. Модели изменены вместе с миграциями, миграции применяются на чистой БД.
2. Тесты покрывают новый сценарий, запреты и граничные случаи и проходят в Docker.
3. Отсутствуют N+1 запросы на затронутых страницах.
4. Инвалидация кеша реализована через `transaction.on_commit` и проверена тестом.
5. Секреты не попали в код, логи и репозиторий; права проверяются на сервере.
6. `docker compose up --build -d` поднимает приложение на порту `8001`.

### Ревью

Ревью проверяет: соответствие принципам I–VII, отсутствие обходов ограничений БД, корректность
прав доступа, наличие тестов на негативные сценарии, инвалидацию кеша после коммита и
отсутствие лишних зависимостей.

## Governance

Конституция имеет приоритет над привычками, шаблонами и локальными договорённостями. При
конфликте требования конституции выполняются в первую очередь.

- **Поправки.** Изменения вносятся только через процедуру `/speckit.constitution`, с указанием
  причины, затронутых принципов и плана миграции существующего кода. Изменение вступает в силу
  после записи в этот файл.
- **Версионирование.** Используется семантическое версионирование: MAJOR — удаление или
  несовместимое переопределение принципа; MINOR — новый принцип или раздел, существенное
  расширение правил; PATCH — уточнения формулировок без изменения смысла.
- **Сопровождение.** Каждая спецификация, план, набор задач и ревью проверяются на соответствие
  конституции. Несоответствие фиксируется как дефект и устраняется до завершения изменения.
- **Исключения.** Отступление от принципа допускается только с письменным обоснованием в плане,
  явным указанием срока и плана устранения; молчаливые исключения запрещены.
- **Руководство по разработке.** Повседневные инструкции агента и команды запуска находятся в
  `AGENTS.md`; при расхождении с конституцией приоритет у конституции.
